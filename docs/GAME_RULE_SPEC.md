# GoodField ゲームルール・フェーズ・神器授与仕様

- 文書状態: Release 1.0
- 調査基準日: 2026-07-26
- 対象: ゴッドフィールド現行Web版を基準にした互換ルールエンジン
- 対象範囲: 基本状態、勝敗、ターン進行、攻撃と防御、属性、災い、守護神、神器授与、終末の時、公式教典の全神器・全効果

> [!IMPORTANT]
> 公式画面での表記は「経典」ではなく「教典」である。本書は公式教典と複数の非公式Wikiを照合している。調査時の`OPEN-*`は14章で規範規則または明示的な互換範囲として確定済みであり、コメント行の解釈を実装条件にしない。

### 1.2 採用ルール

1. S0とその他の情報源が矛盾する場合はS0を採用する。
2. S0に記述がなく、複数のS1が一致する場合は「Wiki確認済み」として採用候補にする。
3. 単一の非公式情報源にしかない挙動は、本書では断定せず `OPEN-*` にする。
4. 更新時期の異なる情報が矛盾する場合は、新しい記述を自動採用しない。現行Web版で再現テストを行う。
5. カード画像そのものはルール仕様と分離する。カード名、表示値、効果命令、価格、授かり重みは互換ルールの規範データとして本書へ含める。
6. S2Hは処理境界の補強にだけ使う。S0、S0Eまたは14章と衝突する初期値、確率、属性、カード分布は採用しない。採否と差分は `BATTLE_SYSTEM_SPEC.md` 10章へ記録する。

### 1.3 規範語

- `MUST`: 実装が必ず満たす。
- `MUST NOT`: 実装してはならない。
- `SHOULD`: 原則として満たす。例外は記録する。
- `MAY`: 任意。
- `CONFIRMED-S0`: 公式教典で確認済み。
- `CONFIRMED-S0E`: 公式Web版の修行モードで再現・観測済み。
- `CONFIRMED-S1`: 更新日の新しいWikiで確認済み。
- `CONFIRMED-S2`: 補助的な情報源で確認済み。現行実機での再確認が必要。
- `HISTORICAL-S2H`: 旧Flash版を模した非公式実装で構造を確認。単独では現行規則の根拠にしない。
- `OPEN`: 調査時の未確定ID。Release 1.0では14章の確定規則を適用する。

## 2. 用語

| 用語 | 定義 |
|---|---|
| 預言者 | 対戦に参加するプレイヤーまたはCPU |
| 神器 | 手札に存在するカード |
| 奇跡 | MPを支払い、習得後に繰り返し使用できる効果 |
| 授与 | 抽選によって神器を手札へ加えようとする処理 |
| 授与義務 | 補充などにより、今後成功させなければならない授与回数 |
| 使用 | プレイヤーが神器を選択し、確定した行動のコストとして手札から除くこと |
| 捨てる | 通常時に神器を手札から除き、補充を発生させない行動 |
| ささげる | 終末の時に「捨てる」と置き換わり、除いた神器数だけ授与を発生させる行動 |
| 災い | 預言者に付与される持続状態 |
| 守護神 | 預言者に1体まで宿り、条件成立時に自動行動する存在 |
| 終末の時 | 設定されたGF値以降、各授与で悪魔抽選が発生する状態 |
| 原子的効果 | ダメージ、回復、状態付与、カード移動など、途中に別判定を挟まない最小処理 |

### 3.4 生存と昇天

1. HPが0になった預言者は昇天候補になる。
2. 太陽のお守りなどのHP0時効果が存在する場合、昇天確定前に割り込み解決する。
3. 割り込み後もHPが0なら `alive = false` とする。
4. 個人戦は、生存する敵がいない預言者を勝者候補とする。
5. チーム戦は、生存者が存在するチームが1つだけになった場合、そのチームを勝者候補とする。
6. 同一の効果解決で全預言者がHP0になった場合は引き分けとする。`CONFIRMED-S1`
7. 勝敗確定を原子的効果の直後に行うか、効果列・授与列の完了後に行うかは `OPEN-03` とする。
8. 個人戦で操作中の人間が先に昇天しても、複数のCPUが生存している限り試合は継続する。人間は以後の試合を観戦できる。`CONFIRMED-S0E`
9. 昇天済みの預言者は以後の通常手番を得ない。4人戦で2人が昇天した後は、生存する2人の通常手番だけが交互に進行した。`CONFIRMED-S0E`
10. 最後の敵が昇天したGF内で勝者が確定し、結果表示のためだけの追加GFは開始しない。`CONFIRMED-S0E`

## 4. フェーズモデル

### 4.1 GamePhase

```ts
type GamePhase =
  | "LOBBY"
  | "INITIALIZING"
  | "INITIAL_GRANT"
  | "TURN_OPEN"
  | "ACTION_SELECTION"
  | "TARGET_SELECTION"
  | "ACTION_DECLARED"
  | "REACTION_SELECTION"
  | "ACTION_RESOLUTION"
  | "POST_ACTION_GRANT"
  | "TURN_CLOSE"
  | "POST_TURN_AUTOMATIC_EFFECTS"
  | "RESULT_CHECK"
  | "MATCH_ENDED";
```

この列挙はサーバーの状態境界を定義する。公式が全処理順を公開しているという意味ではない。

### 4.2 初期化

```text
LOBBY
  → INITIALIZING
  → INITIAL_GRANT
  → TURN_OPEN
```

`INITIALIZING` で行うこと:

1. ルールセットとカードプールのバージョンを固定する。
2. 参加者、チーム、席順を固定する。
3. 乱数シードを固定する。
4. 各預言者の初期ステータスを設定する。
5. 手番順を無作為に決定する。

`INITIAL_GRANT` で行うこと:

1. 各預言者に9回の授与義務を作成する。
2. 授与義務を順に解決する。
3. 初期授与のプレイヤー順、1枚ずつ交互か9枚ずつかは、結果の分布には影響しないが乱数ログ互換性に影響するため `OPEN-04` とする。

### 4.3 通常ターンの確認済み部分

1. 生存中の預言者1人がアクティブプレイヤーになる。
2. アクティブプレイヤーは、使用可能な神器または習得済み奇跡から行動を構成する。
3. 対象が必要な場合は対象を選択する。
4. 攻撃対象は、使用可能な防具を0枚以上選択して応答する。
5. 宣言された行動を解決する。
6. 使用した神器数に対応する補充が発生する。`CONFIRMED-S1`
7. 病の継続効果は、病を持つ預言者自身のターン終了時に発生する。`CONFIRMED-S1`
8. 守護神は「敵のターンのあと」に25%で行動する。`CONFIRMED-S0`
9. 複数回攻撃では、各攻撃に対して独立した防御選択と解決を行う。使用した防具は次の攻撃では使用不能であり、全攻撃終了後にまとめて補充される。`CONFIRMED-S0E`
10. 行動により攻撃側と防御側が消費した神器の授与は、次のGFカウンターへ進む前に行われる。`CONFIRMED-S0E`
11. 昇天済みの預言者はアクティブプレイヤー候補から除外され、生存者だけで手番を継続する。`CONFIRMED-S0E`
12. 4人GF.1戦では、G.F.17からG.F.22まで生存者2人の表示手番が交互に進んだ。防御応答や昇天表示のために別のGF値は増加しなかった。`CONFIRMED-S0E`
13. 6、7、8、10および勝敗判定のさらに厳密な順序は `OPEN-05` とする。

### 4.4 行動選択

サーバーはクライアントへ、現在選択可能な行動だけを提示しなければならない。

```ts
type LegalAction =
  | UseCardsAction
  | CastLearnedMiracleAction
  | PrayAction
  | DiscardAction
  | SacrificeAction
  | SurrenderAction;
```

最低限の制約:

1. 行動を開始できるのはアクティブプレイヤーだけである。
2. 防御応答は攻撃または相手向けカードの対象になった預言者だけが行える。売る・買う・災い付与・神器除去などの非攻撃効果も解決前に必ず応答を挟み、通常防具ではなく「何でもはね返す」効果または「許す」を選ぶ。反射・弾きなどの対象変更後は `OPEN-06`。
3. 「祈る」は使用可能な武器がない場合だけ選択でき、神器を1枚授かる。`CONFIRMED-S1`
   - 修行では祈るボタン自体は常時表示されたが、使用可能な武器がある状態で押しても何も起こらなかった。`CONFIRMED-S0E`
4. 習得済み奇跡は必要MPを支払える場合に使用できる。`CONFIRMED-S1`
5. 奇跡を唱えるたびに元の奇跡神器を再度消費することはない。
6. 通常時は「捨てる」、終末の時は同じ操作位置が「ささげる」になる。`CONFIRMED-S0`
7. 武器、太陽のお守り、あぶないウスは通常の「捨てる」で捨てられない。`CONFIRMED-S0`
8. 通常武器は同時に1枚だけ選択できる。別の通常武器を選ぶと選択が置き換わる。`CONFIRMED-S0E`
9. 加算可能な奇跡は通常武器と同時に使用できる。初回使用時は奇跡神器が手札から習得済み奇跡へ移動し、MPを消費する。通常武器と奇跡神器の両方が補充対象になる。`CONFIRMED-S0E`
10. 4人戦で単体攻撃武器を選択すると、生存中の敵1人が対象欄へ直ちに表示された。行動確定前に別の生存中の敵パネルを選ぶと、対象欄がその敵へ変更された。`CONFIRMED-S0E`
11. 武器選択直後に表示される既定対象の決定規則は `OPEN-25` とする。

## 5. 攻撃、防御、属性

### 5.1 ダメージ

通常ダメージは次式とする。

```text
residualDamage = max(0, totalAttack - totalDefense)
```

`totalAttack` と `totalDefense` にどの補正をどの順序で加えるかは、個別効果仕様で定義する。

### 5.2 属性

内部表現は次の7値とする。

```ts
type Element = "NONE" | "FIRE" | "WATER" | "WOOD" | "EARTH" | "LIGHT" | "DARK";
```

公式教典で確認した防御可能関係:

| 防御属性＼攻撃属性 | 無 | 火 | 水 | 木 | 土 | 光 | 闇 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 無 | 可 | 不可 | 不可 | 不可 | 不可 | 不可 | 可 |
| 火 | 可 | 不可 | 可 | 不可 | 不可 | 不可 | 可 |
| 水 | 可 | 可 | 不可 | 不可 | 不可 | 不可 | 可 |
| 木 | 可 | 不可 | 不可 | 不可 | 可 | 不可 | 可 |
| 土 | 可 | 不可 | 不可 | 可 | 不可 | 不可 | 可 |
| 光 | 可 | 可 | 可 | 可 | 可 | 不可 | 可 |
| 闇 | 可 | 不可 | 不可 | 不可 | 不可 | 不可 | 可 |

追加規則:

1. 光攻撃は通常の属性防具では防御できない。`CONFIRMED-S0`
2. 闇攻撃は全属性で防御できる。`CONFIRMED-S0`
3. 闇攻撃で1以上の残余ダメージを受けた場合、通常の減算ではなくHPを0にする。`CONFIRMED-S0`
4. 異なる属性の神器を同時使用した攻撃は無属性になる。`CONFIRMED-S0`
5. 光属性は火、水、木、土の代用になり、光とそれらを組み合わせた場合は対応する非光属性になる。`CONFIRMED-S0`
6. 3種類以上の混合、闇を含む混合、「染める」効果との優先順は個別効果仕様および `OPEN-07` で確定する。

### 5.3 全体攻撃

1. `%`付き武器は敵全体を対象とし、各対象に命中率判定を行う。`CONFIRMED-S1`
2. 暗雲状態の預言者に対する全体攻撃は必ず命中する。`CONFIRMED-S0`
3. 対象ごとの命中判定順、応答順、効果解決順は `OPEN-08` とする。

## 6. 災い

### 6.1 病

| 状態 | 自分のターン終了時 | 自然悪化 | 重ねがけによる悪化 |
|---|---:|---:|---|
| 風邪 | HP-1 | 5%で熱病 | 病を受けると熱病 |
| 熱病 | HP-2 | 5%で地獄病 | 病を受けると地獄病 |
| 地獄病 | HP-5 | 5%で天国病 | 病を受けると天国病 |
| 天国病 | HP+5 | 5%でHP0 | 病を受けるとHP0 |

公式教典は「毎ターン」と記載するが、Wikiでは「自分のターン終了時」と具体化されている。自然悪化もWikiではターン終了時である。継続効果と悪化判定の前後は `OPEN-09` とする。

### 6.2 その他の災い

| 状態 | 効果 |
|---|---|
| 霧 | 敵を対象とする神器の対象者が敵の中から無作為に選ばれ、敵ステータスが見えなくなる |
| 閃光 | 1回の防御で使用できる神器が最大1枚になる |
| 夢 | 授かった神器が50%で別の神器に見える |
| 暗雲 | 自分が対象となる全体攻撃が必ず命中する |

夢による表示用神器の抽選範囲、真のカードと偽表示の確定タイミングは `OPEN-10` とする。

## 7. 守護神

公式教典で確認済み:

1. 守護神は敵のターン後に25%で行動する。
2. 守護神はダメージを受けたとき10%で去る。
3. 地球神は取引、武器、防具、雑貨を使用する。
4. 月神は奇跡を使用する。

Wiki補足:

1. 同じ守護神が複数の預言者へ同時に宿ることはない。
2. 現行守護神は独立HPを持たない。
3. 「守護神がダメージを受ける」は、宿主がダメージを受けた場合を意味するとされる。

次の点は調査時に未確定だった。実装規則は14章を正本とする:

- 複数の敵守護神が同じターン後に判定対象になる場合の順序: `OPEN-11`
- 守護神行動後に別の守護神判定や勝敗判定を継続するか: `OPEN-12`
- ダメージ0、反射、自傷、病ダメージで離脱判定するか: `OPEN-13`

## 8. 神器授与と補充

### 8.1 カードプール

1. 標準カードプールは、カードIDと整数の授かり重みを持つ。
2. 2026-07-24の公式定義で通常時の総重みは500、通常授与候補は237件である。`CONFIRMED-S0`
3. 1回の授与ごとにプールを元へ戻す復元抽選とする。したがって同じ神器を連続で授かり得る。`CONFIRMED-S1`
4. 物理的な山札、残枚数、捨て札山は存在しない。
5. 標準パックの全候補と重みは8.6節を規範とし、合計500を自動テストする。

```ts
type CardPoolEntry = {
  cardDefinitionId: string;
  weight: number; // positive integer
};
```

### 8.2 授与義務

補充処理を安全に扱うため、「カードを直接引く」のではなく授与義務をキューへ積む。

```ts
type GrantObligation = {
  obligationId: string;
  playerId: string;
  reason:
    | "INITIAL_HAND"
    | "USED_CARD_REPLACEMENT"
    | "PRAYER"
    | "SACRIFICE"
    | "CARD_EFFECT"
    | "OTHER";
  remaining: number;
};
```

確認済み:

1. 初期手札では1人9回の授与が必要である。
2. 使用した手札は、使用枚数と同数が補充される。`CONFIRMED-S1`
3. 祈りは1回の授与を発生させる。`CONFIRMED-S1`
4. 通常の「捨てる」は補充を発生させない。
5. 終末時の「ささげる」は、除いた神器数と同数の授与を発生させる。`CONFIRMED-S1`
6. 攻撃に使った通常武器は1枚につき1回の授与義務を作る。`CONFIRMED-S0E`
7. 防御に使った防具は1枚につき1回の授与義務を作る。複数回攻撃の途中では解決せず、複合行動終了後に解決する。`CONFIRMED-S0E`

### 8.3 通常時の授与アルゴリズム

終末前の1授与は次の処理とする。

```text
GRANT_ONE(player):
  1. playerが授与可能か確認する
  2. 手札が18枚なら満杯処理へ移る
  3. 標準カードプールから重み付き復元抽選する
  4. CardInstanceを生成する
  5. 夢状態なら表示情報を生成する
  6. 手札へ加える
  7. 授与義務を1減らす
  8. CardGrantedイベントを記録する
```

手札満杯時の処理は状況別に情報が不十分なため `OPEN-16` とする。

### 8.4 終末時の授与アルゴリズム

公式教典では、終末の時以降、神器を授かるたびに25%で悪魔が現れる。

Wikiに記録されている絶対確率:

| 結果 | 確率 | 効果 |
|---|---:|---|
| 通常神器 | 75% | 標準プールから神器を1枚授かる |
| 小悪魔 | 7% | 自分へ10ダメージ |
| 中悪魔 | 5% | 自分へ20ダメージ |
| 大悪魔 | 3% | 自分へ30ダメージ |
| イタズラマン | 5% | 自分の神器または習得済み奇跡を合計2個捨てる |
| めぐみの妖精 | 5% | HP、MP、所持金のいずれか1つを10増加 |

合計は100%であり、悪魔系合計が公式記載の25%と一致する。

Wikiでは、悪魔効果後も同じ授与を完了させるため再抽選し、悪魔が連続する可能性がある。また、イタズラマンが捨てた2個は追加補充されない。

暫定アルゴリズム:

```text
RESOLVE_END_TIME_GRANT(obligation):
  while obligation.remaining > 0:
    if 対象が昇天済み:
      対象の残り授与義務を破棄して終了する

    outcome = weightedChoice({
      STANDARD_ARTIFACT: 75,
      SMALL_DEMON: 7,
      MEDIUM_DEMON: 5,
      LARGE_DEMON: 3,
      MISCHIEF: 5,
      FAIRY: 5
    })

    if outcome == STANDARD_ARTIFACT:
      標準プールから神器を復元抽選
      手札へ加える
      obligation.remaining -= 1
    else:
      悪魔効果を即時解決
      // obligation.remainingは減らさない

    原子的効果後のHP0処理を行う
    HP0が確定した場合は対象の残り授与義務を破棄する
```

修行GF.1で次を実機確認した。

- めぐみの妖精が所持金を10増加した後、同じ授与義務が継続し、さらに残っていた2枚分まで手札が補充された。`CONFIRMED-S0E`
- イタズラマンが神器2枚を除いた後、悪魔を発生させた元の授与義務だけが継続した。盗まれた2枚分の追加補充はなかった。`CONFIRMED-S0E`
- 大悪魔の30ダメージで授与対象が昇天した場合、その対象へ通常神器を追加授与せず、勝敗条件成立時は同じGFカウンターのまま結果が確定した。`CONFIRMED-S0E`

次は調査時に未確定だった。実装規則は14章を正本とする:

- 妖精の増加先が完全等確率か: `OPEN-18`
- イタズラマンが2個未満しか捨てられない場合の処理: `OPEN-19`
- 悪魔連鎖に実装上の上限が存在するか: `OPEN-20`

### 8.5 手札上限

確認済み:

1. 通常の手札上限は18枚。
2. 18枚の状態では通常授与で単純に19枚へ増やせない。
3. Wikiには、19枚目を他者から押し付けられた場合、既存手札から無作為に1枚が消えるという記録がある。
4. Wikiには、18枚で祈ると無作為の神器が捨てられるという記録がある。

次の区別を必ず仕様化する必要がある。

```ts
type HandOverflowCause =
  | "NORMAL_GRANT"
  | "PRAYER"
  | "PURCHASE"
  | "FORCED_TRANSFER"
  | "GUARDIAN"
  | "CARD_EFFECT";
```

各原因で、新規カードを拒否するのか、既存カードを無作為破棄するのか、新規カードを含めた全19枚から破棄するのかは `OPEN-16` とする。

## 9. 終末の時

1. 部屋設定は終末なし、GF.1、GF.50、GF.75、GF.100、GF.150が記録されている。`CONFIRMED-S1`
2. GF.Nは、試合全体で数えたN回目の行動付近で終末に入るとされる。
3. 終末移行後は、各授与で25%の悪魔抽選を行う。`CONFIRMED-S0`
4. 終末移行後は「捨てる」が「ささげる」に置き換わる。`CONFIRMED-S0`
5. GF.1設定では初期手札配布中は `G.F.0 /1` であり、最初の預言者の行動開始時に `G.F.1 /1` となって終末背景へ変化した。したがってGF.Nは少なくともN番目の通常手番開始時には有効である。`CONFIRMED-S0E`
6. GFカウンターが防御、守護神、超常現象の自動行動を個別に数えるかは `OPEN-21` とする。
7. 4人戦で預言者が昇天した後、その預言者用の通常手番は表示されず、生存者の通常手番だけでGF値が1ずつ進んだ。`CONFIRMED-S0E`

## 10. 取引とリソース支払い

Wiki確認済み:

1. 両替はHP、MP、所持金を1:1で再配分する。
2. 売るは自分の神器を相手に売る。
3. 売却価格を相手の所持金だけで支払えない場合、所持金、MP、HPの順に不足分を支払う。
4. 買うは相手の神器を無作為に1つ提示し、購入者が価格を支払える場合だけ購入可否を選択する。
5. 「買う」神器を使用した分は補充され、購入成立時は購入神器も手札へ加わるため、手札が純増し得る。
6. 修行でCPUが自分の神器を「買う」で購入した際、価格2はCPUから自分へ移動し、購入された神器は自分の手札から除かれた。自分側の補充はなく手札は9枚から8枚になった。`CONFIRMED-S0E`
7. CPUが価格15の神器を自分へ「売る」で売却した際、自分の所持金は22から7、CPUの所持金は0から15となり、商品神器が自分の手札へ加わった。`CONFIRMED-S0E`

プロジェクト採用ルール:

1. 「売る」は取引神器と商品神器を手札から除くが、売り手の授与義務は合計1回とする。`PROJECT-22`
2. 「買う」で売り手から移動した商品神器に、売り手の授与義務は作らない。`PROJECT-22`
3. 代金は所持金、MP、HPの順で徴収する。「売る」では不足分がHPを超えても価格全額を徴収したものとして売り手へ加算し、支払者のHPを0へクランプする。`PROJECT-23`
4. 代金処理後に商品を移動し、復活または昇天、勝敗判定、授与の順で処理する。移動した商品が太陽のお守りなら、その支払者のHP0時効果に使用できる。`PROJECT-23`
5. 「買う」はHP、MP、所持金の合計が価格以上の場合だけ購入確認を要求する。価格0でも確認を省略しない。`PROJECT-24`
6. 「買う」で取得した未使用の奇跡神器は手札へ移し、即時習得させない。`PROJECT-24`

## 11. 乱数

互換ルールエンジンの実装要件:

1. サーバーだけが乱数を生成する。
2. `Math.random()` をゲーム判定に使用してはならない。
3. 試合開始時にシードを確定し、同一ルールセット、同一コマンド列、同一シードから同じ結果を再現できなければならない。
4. 確率は浮動小数点境界ではなく整数重みで表現する。
5. 乱数を消費するたび、次をイベントログへ記録する。

```ts
type RandomEvent = {
  eventSequence: number;
  rngIndex: number;
  context:
    | "TURN_ORDER"
    | "CARD_GRANT"
    | "END_TIME_GRANT"
    | "HIT_CHECK"
    | "TARGET_SELECTION"
    | "CALAMITY_WORSEN"
    | "GUARDIAN_ACTION"
    | "DREAM_DISGUISE"
    | "OTHER";
  candidatesHash: string;
  selectedKey: string;
};
```

6. 候補集合の順序はカードID、プレイヤー席順などで正規化し、オブジェクト列挙順へ依存してはならない。
7. クライアントへ秘密情報や将来の乱数状態を送信してはならない。

## 12. イベント解決

ルールエンジンは、状態を直接ばらばらに変更せず、コマンドからイベント列を生成する。

```ts
type GameCommand = {
  commandId: string;
  actorId: string;
  expectedEventSequence: number;
  action: LegalAction;
};

type GameEvent =
  | ActionDeclared
  | CardConsumed
  | AttackCreated
  | DefenseCommitted
  | HitRolled
  | DamageApplied
  | HpReachedZero
  | RevivalResolved
  | CardGranted
  | CalamityApplied
  | GuardianActed
  | MatchEnded;
```

要件:

1. `expectedEventSequence` が現在値と一致しないコマンドを拒否する。
2. 同じ `commandId` を再受信しても二重適用しない。
3. 1つのコマンドで発生したイベント列は順序を固定する。
4. 各原子的効果の後にHP0トリガーの有無を検査する。
5. 勝敗確定タイミングは `OPEN-03` 解決後に固定する。

## 13. 最低限の受け入れテスト

### 13.1 授与

1. 同じ神器が連続授与され得る。
2. 9回の初期授与後、各預言者の手札が9枚になる。
3. 使用した神器N枚に対し、N回の授与義務が作られる。
4. 通常の捨てるでは授与義務が増えない。
5. ささげるN枚ではN回の授与義務が増える。
6. 終末時に悪魔が出ても授与義務が減らず、通常神器を授かって初めて1減る。
7. イタズラマンによる破棄では授与義務が増えない。
8. 同一シードと同一コマンド列でイベントログが一致する。
9. 悪魔で授与対象が昇天した場合、その対象の残り授与義務を破棄する。
10. 相手の買うによって手札から移動した神器は、売り手側の授与義務を作らない。

### 13.2 属性

1. 火攻撃は水または光で防御できる。
2. 水攻撃は火または光で防御できる。
3. 木攻撃は土または光で防御できる。
4. 土攻撃は木または光で防御できる。
5. 光攻撃は通常属性防具で防御できない。
6. 闇攻撃は全属性で防御できる。
7. 闇攻撃の残余ダメージが0なら即死しない。
8. 闇攻撃の残余ダメージが1以上ならHPを0にする。

### 13.3 災い

1. 風邪、熱病、地獄病は自分のターン終了時だけ継続ダメージを与える。
2. 天国病は自分のターン終了時にHPを5回復する。
3. 各病の自然悪化判定は5%である。
4. 閃光中は防御神器を2枚以上選択できない。
5. 暗雲中は全体攻撃の命中率を100%として扱う。
6. 霧中の敵対象は生存する敵から無作為に選ぶ。

### 13.4 勝敗

1. 個人戦で敵が全員昇天したとき勝者候補を作る。
2. 同一効果で全員HP0なら引き分け候補を作る。
3. HP0時効果を解決する前に昇天を確定しない。

### 13.5 複数回攻撃

1. 二回攻撃は2つの独立した防御応答窓を作る。
2. 1回目で使用した防具は2回目の候補に含めない。
3. 1回目と2回目の間に防具を補充しない。
4. 2回目解決後、使用した防具の合計枚数分だけ授与義務を解決する。

### 13.6 多人数の脱落と決着

1. 4人個人戦で操作プレイヤーだけが昇天しても、残り3人で試合を継続する。
2. 昇天済みプレイヤーへ `ACTION_SELECTION` を作らない。
3. 生存者が2人になった後は、その2人だけへ交互に `TURN_OPEN` を作る。
4. 最後の敵がG.F.N内で昇天した場合、G.F.Nのまま `MATCH_ENDED` へ遷移する。
5. 観戦中の元操作プレイヤーにも、勝者名と最終盤面を配信する。

| OPEN-09 | 5%の病悪化判定後、悪化後の病効果を適用する。天国病は発作判定後、生存時に回復する。 |

| OPEN-15 | 強制破棄と「買う」で売り手から移動した商品には補充を作らない。「売る」の取引神器と商品神器は合計1回補充する。 |

| OPEN-21 | 防御と守護神ではGFを増やさず、超常現象の自動行動では増やす。 |

### 14.3 プロジェクト判断

1. 互換対象は2026-07-24時点の現行Web版へ固定する。
2. 公式実装の乱数列ではなく、確率、処理順、結果を互換対象とする。
3. 表示テキストはカード定義から分離し、効果互換を維持したまま差し替え可能にする。
4. カスタムカードと標準外タイミングは初回リリース範囲外とする。
5. オンライン切断時は15秒の期限後にCPU代行へ移し、修行は入力期限なしとする。
6. 初回リリースは2～9人個人戦とし、チーム戦固有の勝敗表示は対象外とする。

### 15.2 観測だけから断定しなかった事項

以下は観測ログ単独では断定しなかった履歴である。Release 1.0の実装は14章の
規範規則を適用する。

1. LIVE-13の直前にはCPUへ守護神が宿っており、自分のHPが10減少していた。ただし画面遷移が速く、守護神行動と補充の前後関係を一意に確定できなかった。
2. 攻撃側と防御側の両方に授与義務がある場合、攻撃側の補充結果が先に表示されたように見えたが、全カード構成を確認できないため観測だけでは処理順を断定しなかった。
3. 妖精の増加先は1回だけ所持金だったため、観測だけではHP、MP、所持金が等確率と断定しなかった。
4. CPUの非公開手札は直接確認できないため、観測だけでは「売る」の売り手側補充枚数を断定しなかった。
5. クリック操作とアニメーション表示の間には遅延があるため、表示開始順だけを内部イベント順の根拠にしない。
6. LIVE4-03で最初に「ょへ」が選ばれた規則は確認できない。対象決定に乱数を使う、席順で決める、またはUIだけの既定表示である可能性を区別できない。
7. 4人戦では全体攻撃を観測できなかった。実装順は14章の`OPEN-08`確定規則を適用する。
