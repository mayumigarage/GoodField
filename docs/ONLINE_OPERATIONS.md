# 招待制オンライン版 運用手順

更新日: 2026-07-26

## 配備

1. 変更不能なコミットから `deploy/Dockerfile` をビルドし、イメージdigestを記録する。
2. ステージングDBをバックアップし、`POSTGRES_DURABLE_STORE_MIGRATIONS`を
   トランザクションで適用する。
3. ステージングへ1台配備し、`/health/live`、`/health/ready`、`/metrics`を確認する。
4. 独立した2ブラウザで、作成、招待参加、準備、開始、再読み込み、決着を実施する。
5. 本番で新規参加をドレインし、進行中試合がないかチェックポイント済みになるまで待つ。
6. 新イメージを1台起動し、ready後にトラフィックを切り替える。本番スモーク後に
   旧イメージを停止する。

## 監視と通知

- `/health/live` はプロセス監視、`/health/ready` はトラフィック投入判断に使う。
- `goodfield_persistence_failures_total` が増加、readyが5分継続して失敗、
  HTTP 5xxが5分平均2%超、WebSocket接続が900超、API p95が300ms超、
  配信p95が500ms超で通知する。
- 構造化ログへ時刻、リクエスト種別、匿名化room/match参照、結果コード、所要時間を残す。
  Cookie、CSRF、招待コード、再参加トークン、手札、PRNG状態は記録しない。

## バックアップと復旧

- PostgreSQLは日次スナップショットと継続WALを暗号化して別障害ドメインへ保存する。
  日次バックアップは7日、週次は4週保持する。
- 月1回、隔離DBへ復元し、ルームチェックポイント、試合Revision、eventSeqの連続性を
  検証する。
- 障害時は書込みを止め、最新の整合するスナップショットとWALへ復元する。readyを
  戻す前に進行試合をロードし、各ブラウザを差分同期または完全同期させる。

## ロールバック

1. 新規参加をドレインし、DBバックアップ時刻と現在のスキーマ版を記録する。
2. 後方互換な変更は直前のイメージdigestへ戻す。
3. 非互換な変更はDBを事前スナップショットへ復元してから直前イメージへ戻す。
4. ready、2ブラウザスモーク、既存試合の再接続を確認してドレインを解除する。

## 停止とインシデント対応

- 計画停止は招待作成と参加を止め、進行試合の終了またはチェックポイントを待って
  SIGTERMする。
- 秘密漏洩時は該当Secretをローテーションし、全セッションと招待を失効する。
- データ破損時は書込みを停止し、証跡を保全して復元手順を実行する。
- 影響範囲、開始・検知・復旧時刻、利用者向け回避策を公開し、72時間以内に再発防止を
  記録する。
